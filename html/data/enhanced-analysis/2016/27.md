## 答案

**B**。因为使用 `TSL (Test and Set Lock)` 实现互斥时，未进入临界区的进程会在 `while (TSL(&lock))` 中持续自旋检查，属于忙等待，不会主动放弃 CPU。

## 解析

题干给出的伪代码为：

`do { ... while (TSL(&lock)); critical section; lock = FALSE; ... } while (TRUE);`

这里的关键是理解 `TSL` 的机制：

- `TSL` 是硬件提供的原子操作，用于“测试并上锁”。
- 当某进程执行 `TSL(&lock)` 时，如果锁已被占用，则返回“已加锁”的结果，该进程不能进入临界区。
- 不能进入临界区的进程不会睡眠，也不会阻塞，而是反复执行 `while (TSL(&lock))` 检查锁是否释放。

因此，这种方式属于**忙等待（spin / busy waiting）**。忙等待的本质是：进程为了等锁，会持续占用处理机时间片执行循环检查。它可能在某一时刻处于：

- **运行态**：正在 CPU 上执行 `while (TSL(&lock))`
- **就绪态**：时间片用完，被调度器换下，等待再次获得 CPU

但它**不会因为等待临界区而进入阻塞态**。由此可以直接推出：

- 不存在“退出临界区的进程去唤醒阻塞进程”的过程；
- 等待者不会主动让出 CPU；
- 该机制不满足“让权等待”；
- 若把这段自旋过程放在关中断状态下执行，会使系统长时间无法响应中断和调度，风险很大。

所以正确选项只能是 **B**。

## 选项分析

A. 退出临界区的进程负责唤醒阻塞态进程

错误。  
本题中的等待方式不是阻塞等待，而是自旋等待。等待进入临界区的进程一直在反复执行 `while (TSL(&lock))`，因此它处于运行态或就绪态，而不是阻塞态。既然没有阻塞态进程，就谈不上由退出临界区的进程去“唤醒”它们。

B. 等待进入临界区的进程不会主动放弃 CPU

正确。  
进程一旦未获得锁，就会持续执行：

`while (TSL(&lock));`

这说明它在不断轮询锁变量，需要 CPU 支持这一循环执行。也就是说，它不是主动挂起自己，而是在忙等待，因此不会主动放弃 CPU。

C. 上述伪代码满足“让权等待”的同步准则

错误。  
“让权等待”要求：进程暂时不能进入临界区时，应立即释放处理机，避免无意义地消耗 CPU。  
而本题中的 `TSL` 方案恰恰是不断自旋检查锁，属于典型忙等待，因此**不满足**“让权等待”。

D. `while (TSL(&lock))` 应在关中断状态下执行

错误。  
`TSL` 本身依靠硬件保证原子性，并不是要求把整个 `while` 自旋循环都放到关中断状态下执行。  
如果在关中断状态下长期执行该循环，那么一旦锁迟迟不可用，当前进程会一直自旋，而系统又无法正常处理中断和进行调度，可能导致其他进程得不到运行机会，造成严重的系统响应问题，甚至形成近似死循环式的 CPU 占用。

## 易错点

- 容易把 `TSL` 和信号量的阻塞等待混淆。  
  信号量可能让进程阻塞；`TSL` 自旋锁是忙等待，不阻塞。

- 容易误判“等待进程的状态”。  
  本题中等待者不在阻塞态，只可能在运行态或就绪态之间切换。

- 容易把“原子操作”误解为“必须关中断执行整个循环”。  
  应区分：`TSL` 指令本身是原子的，但这不意味着外围的 `while` 自旋应长期在关中断状态下执行。
